## 权威性与搬迁说明

- **唯一权威需求基线**：本目录。需求变更只改本目录文件并提升版本。
- `docs/requirements.md` 是**兼容入口**，仅指向本目录，不再承载正文，避免两套内容漂移。
- 编号与版本**原样沿用**：R001–R004、`v0.1` 正式基线。本次搬迁**不修改业务含义**，
  不做静默改写。
- 搬迁过程中若发现旧需求与真实代码存在差异，**只如实记录，不在本轮偷偷改业务规则**：
  差异与限制统一写在 [`implemented-behavior.md`](implemented-behavior.md) 的
  “需求与实现的对照与差异”一节，并注明“不以实现反向改写需求”。

## 版本与变更流程

- 当前需求版本：`v0.1`（正式基线，R001–R004 无遗留歧义，Q-001 已关闭）。
- 交互改进层版本：**`v0.13`（UX021，当前权威，T050 主代理 2026-10-04 已独立验收接受；T007 pending / 系统 Gate 未通过）**；`v0.12`（UX020）–`v0.3`（UX011）
  仅在其**未被后续版本覆盖的部分**继续有效；`v0.2`（UX001–UX010）
  **已实现，历史保留**。见
  [`interaction-improvements.md`](interaction-improvements.md)。
- 契约版本：`usage plan` 解析 `v0.1`；**持久快照契约格式版本 1（v0.3 冻结，已接入）**，
  见 [`../contracts.md`](../contracts.md)。
- 变更流程：先更新 [`product-requirements.md`](product-requirements.md) 并提升版本，
  再同步受影响文档（契约见 `../contracts.md`，证据见 `../verification.md`）。
- **例外（不强制升版）**：仅为**引用已有明确规则**做澄清时，可保留基线版本，
  但**必须记录所引依据**；未确认前不得把建议或假设写成生效规则。
  维护与证据口径以 [`../README.md`](../README.md) 为准。
- 交互改进变更：登记到
  [`interaction-improvements.md`](interaction-improvements.md)，并同步
  [`../tasks.md`](../tasks.md) 的任务与状态；实现并有证据后更新状态。
- 行为发生变化时，同步更新 [`implemented-behavior.md`](implemented-behavior.md)；
  需求与实现冲突时以需求为准，并登记未决问题到 [`../decisions.md`](../decisions.md)。
- 维护与证据要求以 [`../README.md`](../README.md)（docs 文档规范）为准。
- **历史说明**：v0.1 / v0.2 的**实现轮**（已改动 `src/` / `tests/`，并运行构建 / 单元测试 /
  离线冒烟 / 真实脱敏查询）**已发生并留有记录**（见 [`../verification.md`](../verification.md)）。
  本文档的**流程规范更新不提升业务 `v0.1` / 交互 `v0.2`**，也不改需求含义。
