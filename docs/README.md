# 文档规范与索引（docs/README）

本文件是 `ark_left` 项目 **docs/ 文档的维护规范与索引**（权威、简洁）。
它规定各文档的职责、编号与版本规则、需求 / 任务 / 证据链、验证证据要求与系统交付 Gate。

> 外部依据（**绝对来源路径**，非本项目文件）：
> `%USERPROFILE%\multi-agent-development-framework.md` 的
> 第 7 节（子任务交接模板）、第 8 节（Definition of Done）、
> 第 9 节（并发、嵌套与任务生命周期边界）、第 11 节（确认与 `BLOCKED_DECISION` 机制）、
> 第 12 节（子代理直接通信机制）。本文件把框架落在本项目实际文档上；
> 框架有更新时以框架为准并同步修订本文件。
> 项目协作规则与写入所有权约定见 [`../AGENTS.md`](../AGENTS.md)（本项目内约定，非全局配置）；
> 项目说明与构建 / 启动命令见 [`../README.md`](../README.md)。

## 2. 编号与版本

- **需求编号**：`RXXX`（业务需求）；`UXxxx`（交互改进项，属需求细化）。
- **问题编号**：`Q-XXX`；**任务编号**：`T-XXX`（**逻辑任务**的稳定标识）。
- **需求版本**：`v0.1`（正式业务基线）、`v0.13`（交互改进层当前权威，UX021，T050 主代理 2026-10-04 已独立验收接受；`v0.12`–`v0.3` 未被覆盖部分继续有效，`v0.2` 为历史）。
- **契约版本**：如 `usage plan` / 技术栈约定，随 [`contracts.md`](contracts.md) 变化提升。
- **规则**：
  - 编号唯一、稳定；已发布编号**不得复用**或改指其它内容。
  - 需求变更**提升版本**并记录在正式需求文件；同类版本**原样沿用**既有编号，不静默重编。
  - **例外（不强制升版）**：仅为**引用已有明确规则**做澄清时，可保留基线版本，
    但**必须记录所引依据**；未确认前不得把建议或假设写成生效规则。
  - 历史版本与历史记录**保留，不抹除、不回填**；不得把未记录的历史补写成"0"或"已确认"。

## 3. 先基线后实现

1. 需求先形成**可编号、可验收**的基线（含异常与边界），再进入实现。
2. 接口 / 数据模型先冻结契约版本，再并行实现；契约变更走 [`contracts.md`](contracts.md) 并提升版本。
3. **关键歧义未确认前**，暂停受影响实现，登记 `Q-XXX` 为 `OPEN`，任务置 `blocked_decision`；
   等待期间只推进不依赖该问题的独立工作。
4. 有依据或获授权的结论记录为 `DECIDED`，**受影响代理确认采用版本及其任务影响**后，方恢复相关工作；
   **建议、超时、无人回复都不算批准**。
5. `DECIDED` 只表示已有答案；`CLOSED` 需决定落实且相关验证通过，才表示该问题闭环。

## 4. 双向需求—任务—证据链

- 每个需求编号至少对应：可验收场景 **+** 至少一组测试 / 检查证据。
- [`tasks.md`](tasks.md) 中每个任务标注**对应需求编号或必要技术工作**，并给出证据位置。
- 每条业务用例标注其覆盖的需求编号；纯技术工作（重构、构建修复）关联技术任务并说明与交付的关系。
- 交付时输出**需求覆盖表**：哪些需求已验证、哪些未验证及原因；覆盖表不得有未解释缺口。
- 证据必须能反向指回需求与任务；无法追溯的"通过"不计入覆盖。

## 5. 验证证据要求

每条验收 / 验证记录**至少**能追溯到：

- **执行的命令或操作**；
- **运行环境**（OS、编译器 / 运行时、关键版本）；
- **代码 / 文档版本标识**；
- **结果位置**（输出文件、日志、脚本路径或记录条目）。

版本标识口径：

- 项目**有 Git 时**，记录 commit / tag；若工作区存在**未提交变更**，须同时标注 `dirty`
  并附相关文件的**快照标识**（仅记录单个 commit **不足以**复现实际验证状态）。
- 项目**无 Git 时**，**不得仅凭任务编号或时间戳声称可复现**；应保存相关文件的
  **SHA256 清单**或归档副本，并记录结果位置，供后续逐文件核对。
- **不得伪造版本标识或证据**：未执行、无法执行或不适用，一律显式标注"未执行 / 人工未测 / 不适用"，
  **不写成"通过"**。
- 历史版本与历史记录**保留**：新轮次用新记录追加，不覆盖旧记录，也不把旧轮次回填为新版本。

- **记录与执行分工**：文档收尾可采用主代理明确提供的命令 / 环境 / 版本 / 结果，并注明实际执行者与来源；writer 未执行不得署名自测，记录不代替主代理独立验收。证据缺少关键信息或与实际相关文件矛盾时，只核实疑点并反馈。不得仅因记录已有验证就自动重新读取源码或重复构建 / 业务测试；仅在任务要求或发现相关变动、失败或明确疑点需要复验时执行相应检查。
- **按需读取**：先按任务号 / 章节 / 符号搜索定位再局部读取；小文件或确需全文件上下文可整读；相关文件 SHA256 计算不需读内容到模型；历史保留不意味着读取全部历史，也不沿文档链接递归全量读取。
- **上下文控制**：子代理上下文预算、必读窗口、可观察异常与 `NEEDS_HANDOFF` 交接的详细规范见 [`development-plan.md`](development-plan.md) **§9 子代理上下文控制**；子代理**有界再委派**（层数 / 边界 / 所有权 / 逐级审查与汇总）的详细规范见 **§10 有界再委派**；**短任务优先派发**（复杂度分流、默认层数 `0` 直接执行、短任务单字段与小任务记录原则）见 **§11 短任务优先派发**；本文件只写短引用。小任务采用**简短完成记录**，不强制同步所有文档或新增完整交接书，但**需求 / 契约实质变化仍走基线**。

## 6. 未验证项接受与系统交付 Gate

- **任务完成（DoD）**：对应需求已实现且范围一致；风险匹配的测试 / 检查通过；
  契约未被单方面更改；修改清单内文件通过静态检查与审查；无未声明的范围外改动；
  影响验收的关键问题已关闭；关键结论与决定已写入共享记录，**受影响代理已确认采用版本及任务影响**；
  且**经主代理验收**。**任务返回、交接（`NEEDS_HANDOFF`）或 `BLOCKED_DECISION` 都不等于完成。**
- **系统交付 Gate**（框架第 4、8 节）：需求覆盖表完整、集成与端到端验收通过、
  影响本次验收的关键问题**全部关闭**、**未验证项已显式标注并被接受**、获得项目权限批准。
- **"已说明风险"不能代替关键业务问题的确认**；如正式调整范围，应更新基线并重新验收。
- 未验证项可以是**人工视觉 / 交互 / 真实账号**等，但必须：显式列出、说明原因、有跟踪任务
  （如 T-007）、且经有权者**接受**后才随系统交付；**不得**把自动证据冒充为人工验收。

- **第 11 节 确认机制**：`BLOCKED_DECISION` 跨会话仍阻塞；`DECIDED` 恢复须确认版本；

- **第 12 节 直接通信**：无实时通信能力时由主代理中转；共享文件**不是**通知渠道；
  信息交流不构成批准。见 [`tasks.md`](tasks.md)「通信与交接」与 [`decisions.md`](decisions.md)。
